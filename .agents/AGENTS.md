## 一、 任务场景方法论 (Scenarios)

### 1.1 Bug 修复任务方法论 (bugfix)

#### 目标
以最小改动修复已确认的问题，优先恢复正确行为，避免顺手重构和需求扩张。

#### 工作方式
- 先明确现象、触发条件、预期行为；信息不足时先补最小复现路径。
- 先定位根因，再修复表象；不要靠注释报错、跳过校验或增加绕过逻辑来“修好”。
- 修改范围只覆盖与当前缺陷直接相关的代码路径，避免把 bugfix 变成重构。
- 涉及多个可疑点时，优先验证最可能的根因，不要同时引入多种修复手段。

#### 修复要求
- 修复必须能解释“为什么会错”与“为什么这样改能修好”。
- 不为假设场景增加兼容层、开关或抽象，除非当前缺陷确实需要。
- 如果问题本质是规则缺失、边界不清或接口约定错误，先补规则或约束，再补实现。
- 对外部输入、边界条件和错误分支的处理，只补当前缺陷必需的部分。

#### 验证要求
- 至少验证：问题能复现、修复后不再复现、相关主路径未被破坏。
- 优先运行最小必要验证；如果仓库已有对应测试或构建检查，优先复用。
- 无法完成验证时，明确说明未验证项、风险和建议的下一步。

---

### 1.2 代码审查任务方法论 (code_review)

#### 目标
识别改动中的真实风险，给出基于证据、可执行、按优先级排序的审查意见。

#### 审查原则
- 先看正确性，再看稳定性、可维护性、一致性，最后看风格问题。
- 只指出会影响行为、质量、协作效率或后续维护成本的问题；不要把个人偏好包装成缺陷。
- 结论必须绑定具体代码位置、触发条件和影响范围，避免空泛评价。
- 不确定的问题要明确标注前提，不要把猜测写成结论。

#### 审查重点
- 是否存在逻辑错误、边界遗漏、状态不一致、接口误用或回归风险。
- 是否引入不必要的复杂度、重复逻辑、过早抽象或隐式约束。
- 是否破坏现有约定，包括目录结构、命名、接口边界和已有规则。
- 是否缺少与改动规模相匹配的验证。

#### 输出要求
- 优先给出 findings，按严重程度排序。
- 每条意见包含：问题、原因、影响、建议方向。
- 没有明显问题时，明确说明“未发现实质性问题”，不要为了 review 而凑意见。
- 与当前目标无关的改进建议单独归类为次要建议，不与必须修复项混在一起。

---

### 1.3 功能实现任务方法论 (feature)

#### 目标
在明确需求边界和验收标准的前提下，以最小必要改动实现新功能，避免顺手重构和过度设计。

#### 工作方式
- 先明确目标、输入输出、触发方式和验收标准；需求有歧义时，先给默认实现方案，再指出可选分歧。
- 先确定改动边界：哪些文件必须改，哪些文件不要碰，哪些行为不能被顺带改变。
- 多步骤功能优先拆成最小闭环：先实现主路径，再补必要边界，不一次性铺开。
- 优先复用现有模式、现有目录结构和现有约定，不额外引入新层级、新抽象或新配置。

#### 实现要求
- 每一处修改都应直接服务当前功能目标，不为假想场景提前设计。
- 不新增只服务单次需求的工具函数、基类、开关或兼容层。
- 涉及公共接口、目录结构、数据结构或配置约定时，先明确影响范围，再实施。
- 如果问题本质是规则缺失或约定不清，先补规则，再补实现。

#### 验证要求
- 至少验证主路径可用、输入输出符合预期、已有关键行为未被破坏。
- 能复用现有测试、构建、关键流程验证时，优先复用。
- 无法完成验证时，明确说明未验证项、风险和建议下一步。

---

### 1.4 重构任务方法论 (refactor)

#### 目标
在不改变既有外部行为的前提下，改善代码结构、可读性、可维护性或可测试性。

#### 工作方式
- 先明确重构边界：哪些行为不能变、哪些模块允许调整、哪些接口必须保持稳定。
- 优先做小步、局部、可验证的调整，避免一次性大改造成回归面过大。
- 先整理重复、耦合和职责混乱的问题，再决定是否抽象；不要为了“更优雅”引入额外层级。
- 重构中发现独立 bug 时，单独标记，不要混在结构调整里一起悄悄修改。

#### 重构要求
- 保持输入输出、公共接口和关键数据结构语义稳定；如需改变，必须先明确说明。
- 删除无用代码时，要先确认其确实不再被当前路径依赖。
- 不创建只服务一次修改的工具函数、基类或配置项。
- 新结构应比旧结构更直接，而不是更抽象、更分散。

#### 验证要求
- 至少验证重构前后的关键行为等价。
- 能跑测试就跑相关测试；没有测试时，用最小可重复方式验证主路径。
- 若存在未覆盖区域，明确指出潜在回归面和建议补充的验证点。

## 二、 技术栈编码规范 (Stacks)

### 2.1 C++ 项目编码规范 (`src/**/*.cpp`, `src/**/*.h`)

#### 编码标准
- 所有代码必须符合 **Google C++ 风格指南**。
- 使用 **4 空格** 进行缩进，禁止使用制表符（Tab）。
- 非成员变量命名使用 **camelCase**，成员变量命名使用 **m_camelCase**，常量命名使用 **UPPER_SNAKE_CASE**。
- 函数和方法名使用 **snake_case** 风格。
- 使用 **const** 修饰不变的变量，避免在函数参数中传递非 const 引用。

#### 库和框架约束
- 必须使用 **C++11** 标准及以上，不允许使用过时的 C++98/C++03 特性。
- 使用 **STL** 作为标准库，尽量避免依赖第三方库。
- 必须使用 **smart pointers**（如 `std::unique_ptr` 和 `std::shared_ptr`）来管理动态内存，避免使用裸指针。

---

### 2.2 Go 项目编码规范 (`src/**/*.go`)

#### 编码标准
- 所有代码必须符合 **Go 官方编码规范**。
- 使用 **gofmt** 格式化工具；函数和变量命名使用 **camelCase**，包名使用 **lowercase**。
- 避免过多的注释，代码自解释，确保简洁和易读。

#### 库和框架约束
- 必须使用 **Gin** 或 **Echo** 作为 Web 框架；使用 **Gorm** 或 **sqlx** 作为数据库库。
- 网络请求必须使用 **http.Client**；使用 **golangci-lint** 进行静态代码分析。
- 避免在代码中硬编码任何 API 密钥或密码，使用 **context.Context** 处理请求超时和取消。

---

### 2.3 PyQt 项目编码规范 (`src/**/*.py`)

#### 编码标准
- 所有代码必须符合 **PEP 8** 编码规范。
- 使用 **snake_case** 命名变量和函数，类名使用 **PascalCase**。
- 函数必须有 **docstring**；避免过长的函数，确保职责单一。

#### 库和框架约束
- 必须使用 **PyQt5** 或 **PyQt6** 提供图形用户界面。
- UI 组件与逻辑代码分离，所有 UI 代码应放在 `ui/` 目录下，功能代码放在 `src/` 目录下。
- 所有图形界面操作应遵循 **信号与槽**（Signal and Slot）机制。

---

### 2.4 Python 项目编码规范 (`src/**/*.py`)

#### 编码标准
- 所有代码必须符合 **PEP 8** 编码规范；每个文件行数不超过 300 行。
- 变量和函数使用 **snake_case**，类名使用 **PascalCase**。

#### 库和框架约束
- 使用 **FastAPI** 提供 RESTful API；使用 **SQLAlchemy** 作为 ORM 库。
- 使用 **pytest** 进行单元测试；使用 **black** 格式化代码。
- 所有敏感信息存储在 `.env` 文件中。

---

### 2.5 Qt 项目编码规范 (`src/**/*.cpp`, `src/**/*.h`, `src/**/*.ui`)

#### 编码标准
- 符合 **Qt 官方编码规范**；使用 **4 空格** 缩进。
- 变量使用 **camelCase**，成员变量使用 **m_camelCase**，类名使用 **PascalCase**。

#### 库和框架约束
- 必须使用 **Qt 5.14** 或 **Qt 6** 版本；使用 **QML** 和 **QtQuick** 进行界面设计与动态交互。
- 网络通信使用 **QtNetwork** 模块。

---

### 2.6 React 项目编码规范 (`src/**/*.{ts,tsx}`)

#### 编码标准
- 所有代码必须使用 TypeScript；变量使用 camelCase，组件使用 PascalCase，自定义 Hooks 以 `use` 开头。

#### 库和框架约束
- 使用 **React 18**；样式统一使用 **TailwindCSS**；网络请求使用原生 `fetch`。
- API 调用封装在 `src/api`，业务组件放在 `src/components`，页面放在 `src/pages`。

---

### 2.7 Rust 项目编码规范 (`src/**/*.rs`)

#### 编码标准
- 符合 **Rust 官方编码指南**；使用 **Rustfmt** 格式化代码。
- 变量和函数使用 **snake_case**，类型和结构体使用 **CamelCase**。避免使用 `unsafe`。

#### 库和框架约束
- 使用 **async-std** 或 **tokio** 进行异步编程；使用 **serde** 进行序列化；使用 **clippy** 进行静态分析。

---

### 2.8 Vue 3 项目编码规范 (`src/**/*.vue`)

#### 编码标准
- 所有组件必须使用 **Vue 3 Composition API** + **TypeScript**；使用 **camelCase** 命名变量，组件使用 **PascalCase**。

#### 库和框架约束
- 使用 **Vue Router** 进行路由管理，使用 **Vuex** 进行状态管理，使用 **Vite** 作为构建工具，使用 **TailwindCSS** 进行样式管理。

5. **context7**: 实时代码与第三方文档检索技能组（如 `find-docs`, `context7-mcp` 等）。
6. **google-workspace-cli**: Google Workspace 自动化工具与角色技能组（如 `gws-gmail`, `gws-docs`, `gws-sheets`, `gws-drive` 等）。
7. **mcp-toolbox-for-databases**: 多数据源交互与维护技能组。
